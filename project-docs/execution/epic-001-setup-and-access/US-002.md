## En tant que administrateur informatique
Je veux créer, modifier les rôles et désactiver les comptes du personnel du CFDC
Afin que seules les personnes autorisées accèdent à l'application, avec les bons droits

## Contexte
S'appuie sur le socle de US-001. Fiche **Utilisateur** de `SOLUTION_DESIGN.md` §6 ; règles d'accès de `PRD.md` §5 et §9. Workstream : WS-01.

Règles :
- pas d'inscription libre ; l'administrateur informatique **ou le coordonnateur** crée un compte ;
- **seul l'administrateur** change les rôles et désactive un compte ; un compte n'est jamais supprimé, son historique reste ;
- une personne peut avoir **plusieurs rôles** : secrétaire, coordonnateur, chef de service du CFDC, formateur, administrateur informatique, direction du CFDC ;
- le **premier compte administrateur** se crée par une commande lancée une fois sur le serveur (affinage de l'Epic 1, Q1).

Ne pas supposer : la connexion n'existe pas encore (US-004) ; tant qu'elle manque, les routes de cette user story se testent par les tests automatiques.

**Affiné le 2026-11-13, avant construction :**
- **Ce que la lecture du code a changé.** Le backend ne contient que la route de santé : table, migration, DAL, BLL, routes et commande sont à créer. Surtout, la fiche demandait un **écran** de gestion des comptes, alors que la connexion n'arrive qu'en US-004 et les menus par rôle en US-007 : un écran construit maintenant ne saurait ni qui est connecté, ni le protéger. **L'écran sort de US-002** et devient **US-009**, construite après US-007 (décision 1A).
- **Badge :** une lettre majuscule **quelconque**, deux chiffres, un tiret, deux chiffres (`[A-Z]\d{2}-\d{2}`, par exemple `B07-42`) ; unique (décision 2B).
- **Premier mot de passe :** le compte est créé **sans mot de passe** ; l'utilisateur reçoit **par email un lien** à usage unique pour le choisir (décision 3B). US-002 met donc en place l'**envoi d'emails** (SMTP configurable ; Mailpit en local), que US-005 et US-006 réutiliseront.
- **Le coordonnateur** peut créer un compte avec tous les rôles **sauf administrateur informatique** (décision 4A).
- **Champs :** nom et prénom **séparés**, badge, **email obligatoire et unique**, téléphone facultatif (décision 5A).
- **Dernier administrateur :** impossible de désactiver le dernier administrateur actif, ni de lui retirer ce rôle (décision 6).
- **Hachage des mots de passe : Argon2id** (décision 7).
- **Journal :** il arrive en US-003 ; les opérations sur les comptes faites avant ne seront pas tracées. Acceptable sur le serveur de test (données fictives).
- **Conséquences du lien par email** (décisions 8 à 12, même jour) :
  - la page **« Choisir mon mot de passe »**, ouverte par le lien, fait partie de US-002 ; elle ne demande pas d'être connecté ;
  - chaque route déclare les rôles autorisés ; tant que la connexion (US-004) manque, elle répond « non connecté », et les tests simulent l'utilisateur. Deux commandes créent des comptes en attendant l'écran : **`create-admin`** (le premier administrateur) et **`create-user`** (un compte et ses rôles), chacune envoie le lien ;
  - sur le serveur de test, les emails partent par **Brevo** (SMTP, offre gratuite), comme pour `fds-pay` ; ses identifiants se saisissent dans Render, jamais dans le dépôt ;
  - le lien de création de compte est valable **48 heures** ;
  - la commande se lance **depuis le poste de l'administrateur**, avec l'adresse de la base Neon : le plan gratuit de Render n'a pas de terminal.

## Critères d'acceptation

### Données
- [ ] La table `users` garde : badge (format `[A-Z]\d{2}-\d{2}`, unique), nom, prénom, email (obligatoire, unique), téléphone (facultatif), rôles (un ou plusieurs, parmi les six du glossaire), canal de double authentification (email par défaut), actif ou désactivé, bloqué ou non, mot de passe haché en **Argon2id** (vide tant que l'utilisateur ne l'a pas choisi).
- [ ] Un badge au mauvais format ou déjà utilisé, un email déjà utilisé ou un rôle inconnu sont refusés avec un message clair en français.

### Création des comptes
- [ ] Une commande crée le **premier administrateur** ; elle refuse de s'exécuter si un administrateur existe déjà.
- [ ] L'administrateur peut créer un compte avec n'importe quels rôles ; le coordonnateur, avec tous les rôles **sauf administrateur informatique** ; aucun autre rôle ne peut créer de compte.
- [ ] À la création, l'utilisateur reçoit **par email un lien** pour choisir son mot de passe ; le lien ne sert qu'une fois et expire après **48 heures**.
- [ ] La page « Choisir mon mot de passe », en français, bleu et blanc, s'ouvre depuis ce lien sans connexion ; un lien expiré ou déjà utilisé affiche un message clair.
- [ ] Les commandes `create-admin` et `create-user` créent un compte et envoient le lien.
- [ ] Le mot de passe choisi respecte la règle (au moins 8 caractères dont un chiffre).

### Gestion par l'administrateur
- [ ] Seul l'administrateur peut changer les rôles d'un compte, et le désactiver ou le réactiver.
- [ ] Il est impossible de désactiver le dernier administrateur actif, ou de lui retirer ce rôle.
- [ ] Il est impossible de supprimer un compte.

### Emails
- [ ] L'envoi d'emails passe par un serveur SMTP configuré par variables d'environnement ; en local, les emails arrivent dans Mailpit.
