## En tant que administrateur informatique
Je veux un socle technique qui démarre d'une seule commande, testé automatiquement et déployé sur un serveur de test
Afin que les user stories suivantes se construisent, se testent et s'essaient sans rien remettre en place

## Contexte
Le dépôt ne contient que la documentation : **aucune ligne de code**. Cette user story pose le socle décidé dans `SOLUTION_DESIGN.md` §5 (pile), §4 (composants), §11 (déploiement) et ADR 1 à 4, selon l'architecture de `project-docs/_ARCHITECTURE_EXPLAINED.md` (backend en couches `entities / dal / bll / api`, frontend en Feature-Sliced Design). Les compétences `scaffold-backend-service` et `scaffold-frontend-app` génèrent les deux squelettes.

Workstream : aucun domaine fonctionnel ; c'est le socle de WS-01 à WS-06.

Décisions de l'affinage de l'Epic 1 (`epic-001-refinement.md`) qui s'appliquent ici :
- **Q2 :** tests `pytest` (unitaires et intégration sur une vraie base PostgreSQL) et Vitest, lancés par GitHub Actions ; pas de seuil de couverture chiffré.
- **Q3 :** un faux serveur d'email, **Mailpit**, dans Docker Compose pour le développement et le serveur de test.
- **Q4 :** le serveur de test est sur un **hébergement gratuit**, avec **uniquement des données fictives** ; hébergeur choisi à l'affinage ci-dessous.
- **Q5 :** `main` protégée : GitHub Actions vert et une relecture approuvée.
- **Q6 :** interface **bleu et blanc**.

Ne pas supposer : aucune table métier, aucun compte, aucune connexion n'existe encore.

**Affiné le 2026-11-12, avant construction :**
- **Ce que la lecture des compétences de squelette a changé.**
  - `scaffold-backend-service` génère une base **SQLite** par défaut : elle est basculée sur **PostgreSQL** (ADR 2), avec le pilote `psycopg`.
  - La compétence exige `PRD.md`, `CLAUDE.md` et `README.md` dans `backend/` : on crée **`backend/README.md`** (commandes, variables d'environnement) et on s'appuie sur `project-docs/PRD.md` et le `CLAUDE.md` de la racine, **sans les copier**.
  - `scaffold-frontend-app` suppose `npm run dev` seul : en conteneur, l'interface est servie par **Nginx**, qui relaie aussi `/api` vers le backend.
- **Organisation :** `backend/`, `frontend/` et `docker-compose.yml` à la racine. Une seule adresse pour l'interface et l'API, ce qui simplifie le cookie de session (ADR 5).
- **Serveur de test : Render, avec la base sur Neon**, comme pour `fds-pay` (choix de l'utilisateur ; Oracle Cloud écarté). Hébergement gratuit, **données fictives seulement**. Limites acceptées pour un serveur de test :
  - le service s'endort après 15 minutes sans visite (environ une minute pour se réveiller) ;
  - les fichiers déposés sont perdus à chaque redémarrage : les documents de cours n'y sont pas conservés ;
  - la base PostgreSQL gratuite de Render expire après 30 jours, d'où **Neon** pour la base ;
  - pas de Docker Compose : chaque conteneur est un service Render séparé ; Mailpit ne sert qu'en local.
- **HTTPS :** l'adresse gratuite `*.onrender.com` le fournit. Un nom de domaine et une migration viendront plus tard.

## Critères d'acceptation

### Backend
- [ ] `backend/` contient un service FastAPI en couches `entities / dal / bll / api`, avec Alembic configuré sur PostgreSQL.
- [ ] `GET /api/v1/health` répond `200` et indique si la base de données est joignable.

### Frontend
- [ ] `frontend/` contient une application React + TypeScript + Vite en Feature-Sliced Design, avec Tailwind, React Router et TanStack Query.
- [ ] La page d'accueil, en français, aux couleurs bleu et blanc, affiche l'état renvoyé par `/api/v1/health`.

### Docker Compose
- [ ] `docker compose up` démarre `frontend`, `backend`, `db` (PostgreSQL) et Mailpit, et la page d'accueil s'ouvre dans Chrome et Edge.
- [ ] Un volume `documents` est prévu pour les documents de cours, et les données PostgreSQL survivent à un redémarrage.
- [ ] Aucune adresse, aucun mot de passe ni aucun fournisseur n'est codé en dur : tout vient de variables d'environnement, avec un fichier `.env.example`.

### Intégration continue
- [ ] GitHub Actions exécute, à chaque pull request vers `main`, les tests backend (sur un PostgreSQL de service), les tests frontend et Steiger.
- [ ] Un test qui échoue fait échouer la CI.
- [ ] `main` est protégée : CI verte et une relecture approuvée exigées.

### Serveur de test
- [ ] L'application tourne sur le serveur de test, sur l'hébergement gratuit retenu, et sa page d'accueil répond.
- [ ] Le README dit comment lancer l'application en local et comment déployer sur le serveur de test, et rappelle que ce serveur ne reçoit **que des données fictives**.
