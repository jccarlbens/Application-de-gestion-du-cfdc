## En tant que administrateur informatique
Je veux un écran pour lister, créer, modifier les rôles, désactiver et réactiver les comptes
Afin de gérer les accès du personnel du CFDC sans passer par une commande sur le serveur

## Contexte
Sorti de US-002 à son affinage, le 2026-11-13 : un écran de gestion des comptes a besoin de la connexion (US-004) et des droits par rôle (US-007) pour savoir qui l'utilise et le protéger. US-002 livre les règles et les routes de l'API ; cette user story livre l'écran qui les utilise. Workstream : WS-01.

Règles reprises de US-002 : le coordonnateur crée des comptes avec tous les rôles sauf administrateur informatique ; seul l'administrateur change les rôles, désactive et réactive ; le dernier administrateur actif ne peut être ni désactivé ni privé de ce rôle ; aucun compte n'est supprimé.

**Affiné le 2026-11-17, avant construction :**
- **Ce que la lecture du code a changé.**
  - Il n'existe **aucune route pour lire un seul compte** (`GET /users` donne toute la liste) : une page par compte en a besoin.
  - Le **déblocage** existe côté serveur (US-004) mais ne figurait pas dans cette fiche ; sans écran, seule la commande `unblock-user` débloque.
  - Le serveur dit déjà si la personne a choisi son mot de passe (`has_password`).
  - Le journal garde des valeurs brutes (`{"is_active": false}`, `{"role": "trainer"}`, `[secret modifié]`) : illisibles telles quelles.
  - Un lien de mot de passe expiré (48 heures) ne peut pas être renvoyé : c'est US-006 (mot de passe oublié) qui comblera ce manque.
- **Disposition** (décision 1A) : une page **liste** (`/comptes`), puis **une page par compte** (`/comptes/<numéro de badge>`) avec ses informations, ses actions et son panneau « Historique ».
- **Création** (décision 2A) : une page `/comptes/nouveau` (numéro de badge, prénom, nom, email, téléphone, rôles en cases à cocher) ; ensuite, « Compte créé : un lien pour choisir le mot de passe a été envoyé à … ».
- **Confirmation** (décision 3) : désactiver, réactiver, débloquer et changer les rôles demandent d'abord une confirmation.
- **Déblocage à l'écran** (décision 4) : un bouton « Débloquer » pour l'administrateur.
- **Historique lisible** (décision 5) : chaque entrée devient une phrase (date, auteur, ce qui a changé) ; un lien « Détails » montre l'avant et l'après pour ce qui ne se traduit pas en phrase.
- **Pas de recherche** (décision 6) : une dizaine de comptes, triés par nom.
- **Qui construit** (décision 7) : l'agent, pour l'administrateur informatique.

## Critères d'acceptation
- [ ] L'administrateur et le coordonnateur voient la liste des comptes : badge, nom, prénom, rôles, actif ou désactivé, bloqué ou non.
- [ ] Ils peuvent créer un compte ; le coordonnateur ne se voit pas proposer le rôle administrateur informatique.
- [ ] L'administrateur peut changer les rôles, désactiver, réactiver et **débloquer** un compte, après confirmation ; les autres rôles ne voient pas ces actions.
- [ ] Un compte créé dont la personne n'a pas encore choisi son mot de passe est signalé « En attente du mot de passe ».
- [ ] Les refus du serveur (badge pris, dernier administrateur…) s'affichent en français.
- [ ] L'écran n'est pas accessible aux autres rôles.
- [ ] Chaque compte a un panneau « Historique » qui affiche son journal (route de US-003), dans l'ordre chronologique, en phrases lisibles, avec « Détails » pour l'avant et l'après (déplacé de US-003 le 2026-11-16).

## Notes de réalisation

*2026-11-17, construction sur la branche `claude/gallant-newton-x8fyao`.*
- **Backend :** `GET /api/v1/users/by-badge/{numéro}`, protégée par `require_roles(administrateur, coordonnateur)` ; un numéro inconnu donne 404 « Aucun compte n'a ce numéro de badge. ». Le test de couverture des routes l'a prise en compte sans rien changer.
- **Frontend :** `entities/account` (appels à l'API, types, statut, tri, phrases de l'historique, pastille de statut) ; pages `accounts`, `account-new`, `account` ; `shared/ui/ConfirmDialog` (fenêtre modale du navigateur, Échap annule) et `AccessDenied`.
- **Steiger a refusé** que l'entité `account` importe directement l'entité `viewer` (les rôles). Les rôles passent par l'entrée prévue par Feature-Sliced Design pour ce cas, `entities/viewer/@x/account`. La pastille de statut, d'abord dans une page, a rejoint `entities/account` : une page n'importe pas une autre page.
- **L'auteur d'une entrée** est nommé (« Ada Admin (Z01-01) ») quand c'est une personne connectée qu'on retrouve dans la liste des comptes ; sinon son libellé (« Ligne de commande (administrateur) »…).
- **Tests :** 180 au backend, 66 au frontend.
- **Vérifié dans Chromium :** l'administrateur voit la liste triée par nom avec rôles et statuts ; crée X09-09 (« Compte créé : un lien … a été envoyé à lea@example.test. », statut « En attente du mot de passe ») ; ajoute le rôle Formateur, désactive puis réactive, chaque fois après confirmation ; l'historique se lit « Ada Admin (Z01-01) : Compte créé (X09-09) / Rôle ajouté : Secrétaire / Rôle ajouté : Formateur / Compte désactivé / Compte réactivé » ; C03-15, bloqué par 5 mauvais mots de passe, est débloqué depuis sa page. Le coordonnateur, sur téléphone, voit les comptes en cartes, n'a pas la case « Administrateur informatique » et aucun bouton d'action. Console sans erreur.
- *2026-11-17 :* **validée par l'administrateur informatique ; la user story passe à Terminé.**
